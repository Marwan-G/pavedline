# Pavedline v0.2–v0.4 — how they are built

Date: 2026-11-08. Status: design, waiting for approval. The product design stays
[`2026-11-07-pavedline-design.md`](2026-11-07-pavedline-design.md) (the main spec); this document decides **how** steps
4–12 get built, proven and merged, and the few places where the main spec changes.

## 1. Intent

Pavedline v0.1 covers steps 0–3. Steps 4–12 turn a spec into a running, deployable product, and that is the part the
founder will rely on when starting a new private product repo. The goal is a plugin whose whole flow works the first
time it is used for real, not one that only passes its own unit tests.

## 2. Goals

- Steps 4–12 from the main spec (§6, §9, §11, §12) work end to end: skills, agents, templates, the stack pack, the
  Helm base chart, GitOps, CI templates, scanners, infra profiles, the cockpit.
- Every step is **proven by running it**, on a private trial project, before its PR merges.
- Few PRs, each complete and working when it opens.
- `main` keeps showing v0.1 until everything is done.

## 3. Non-goals

- No example product in the public repo. No `examples/` folder, no trial outputs, screenshots or Figma links.
- No GitHub release, tag, or version bump during this work (founder, 2026-11-08: "no release changes on GitHub").
  `plugin.json`, `marketplace.json` and `VERSION` stay `0.1.0`; new work is listed under `CHANGELOG.md ▶ Unreleased`.
- No cloud run. Step 12 is proven by static checks plus the local integration wave (main spec §11.6, §17).

## 4. Anti-goals (a failure even if CI is green)

- A skill whose instructions read well but that nobody has executed.
- A stack-pack template that only renders and never builds, boots and deploys.
- A PR that opens half-done and is finished through follow-up PRs.
- Anything private leaking: the founder's real product, its domain or competitors, the trial project, personal
  emails, local paths (main spec §16).

## 6. How a step is built and proven

For each step, in flow order:

1. **Write** the skill(s), agent(s) and templates the main spec lists for that step.
2. **Static checks**: `lint_skills.py`, the skill contract tests (exact wording, question order, outputs named),
   `claude plugin validate`, sanitise scan, `.dot` checks.
3. **Run it on the trial**: execute the step in the trial folder as a user would (the plugin loaded with
   `claude --plugin-dir` from the working branch). Check that every output file the main spec §6 table names exists
   with its expected structure, the gate's question was asked, `STATE.md` points at the next step, and the hooks
   fired where they should. **The trial proves the workflow, not the product (founder, 2026-11-08):** outputs need
   their structure, not polish or completeness; nobody iterates them for quality. For build steps, the step passes
   once the build process starts correctly; no finished, working app is required.
4. **Fix what the run showed** in the plugin, not by hand-editing the trial's outputs, then re-run the step.
5. Record the evidence (step, trial run date, what was checked) in the PR body's short evidence list — no trial
   content.

Code that ships in templates (stack pack, Helm chart, CI templates, profiles) is also proven **in Pavedline's own
CI**, without the trial: a job generates a neutral starter project from the templates and builds, tests, boots and
deploys it to kind. This keeps the proof public and repeatable.

### 6.1 Calls made by the builder (agent), for the founder to check

- **Trial scope.** The trial product is fixed in a private note outside the repo. It is chosen to take the
  conditional branches, not only the happy path (multi-tenant, compliance in scope, all four surfaces); its profile
  stays in that note.
- **Where the main spec has no default** (the visual, a product choice), the agent decides as the trial's founder and
  records the reason. The step-7 visual is approved the same way; the blind design-verifier still runs.
- **How a step is run.** In a fresh headless Claude Code session with the plugin loaded from the working branch
  (`claude -p --plugin-dir …`), continued turn by turn with `--resume`, the agent answering as the founder. That proves
  the skill loads, triggers and asks its questions in a real session, and the hooks fire there.
- **Figma.** Step 7 is proven in Figma or PR 1 does not merge. If the Figma login is missing, the founder is asked to
  log in; there is no "statically checked only" fallback.
- **Mobile CI.** If GitHub's macOS runners are free for this public repo, iOS builds run there; otherwise CI proves
  Android and the JavaScript checks on Linux and the README says iOS is built locally. Recorded either way.
- **CI weight.** Every PR runs a smoke job: the generated starter project builds and deploys to kind with Argo CD and
  a single-instance CNPG. The full run (three instances, backup and restore drill, Gateway API) runs on PRs that
  touch the templates or the cluster scripts, and weekly.
- **CI on `next`.** `ci.yml`'s `pull_request` trigger has no branch filter, so PRs into `next` already run every check;
  the `push` trigger gains `next`. The final `next → main` PR runs everything once more.
- **Scope is by step.** The PR lists in §5 are exhaustive for new skills and agents. Existing skills (`diagram`,
  `project-registry`, `local-cluster`, `state`, `doctor`) are updated in whichever PR's step needs them;
  `design-system-contract` is PR 1, `fastapi-service` PR 2.

## 7. Definition of done, per PR

- Every skill, agent and template of the PR's steps exists, and the main spec's output files for those steps are
  produced on the trial run.
- CI green on the PR (the existing 8 checks + CodeQL, plus any new jobs the PR adds).
- A blind reviewer subagent approves the diff (gates 2 and 3); a blind adversarial subagent too where the main spec
  §9.1 requires 3b (hooks, CI, auth, tenancy, infra, secrets). Findings are fixed or listed `accepted — <reason>`.
- README, flow table, architecture docs and `CHANGELOG.md ▶ Unreleased` describe only what now works.
- PR text: one short line plus the gates line (repo rule).

## 8. Merging

The agent merges by fast-forwarding `next` to the reviewed PR head (`git push origin <branch>:next`), never through
GitHub's merge button, so every commit keeps the noreply committer. `next` therefore has no "pull request required"
rule; a ruleset that blocks force-push and deletion on `next` is recommended (a founder click). The final
`next → main` goes through the `main` ruleset, on the founder's go, with the committer checked before and after.

## 9. Changes to the main spec

- §17 v1.0: "an example product completes steps 0–11 on local" becomes "Pavedline's CI deploys a generated starter
  project to kind on every PR, and a private trial project has completed steps 0–11 on local".
- §17 release rows stay as the content plan; there are no releases during this work (§3 above).
- §13 README status line: unchanged until the final merge.

## 10. Left to the builder

Each `SKILL.md`'s wording; template value names; the order of tasks inside each PR; the Gateway API controller, the
local S3-compatible store and the webhook tunnel (each pinned and verified on the web when chosen, and proposed under
the ask-before-adding rule when it is a new service); the neutral starter project's contents; the trial's folder
location (outside the Pavedline repo).

## 11. Open risks

- **Mobile proof.** Expo builds need macOS for iOS. Whether GitHub's macOS runners are free for this public repo,
  and how long they take, is verified before the job is added; Android and JavaScript checks run on Linux regardless.
- **Hooks in the trial.** The trial is run in this agent's session; hooks only fire inside a Claude Code session with
  the plugin loaded, so hook behaviour is checked with headless `claude -p --plugin-dir` runs.
- **Figma access** depends on the founder's Figma login in the session.
- **Size of PR 2.** Built and reviewed internally in stages; it opens only when all of it works.
